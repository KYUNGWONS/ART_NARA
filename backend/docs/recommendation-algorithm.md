# 추천 알고리즘 설계 문서

## 1. OpenAI API(외부 LLM)를 사용하지 않는 이유

콘텐츠 추천에 OpenAI 같은 외부 LLM API를 붙이는 방안도 검토했으나 채택하지 않았다.

- **비용**: 추천은 사용자가 화면을 열 때마다, 그리고 사용자-콘텐츠 조합마다 반복적으로 계산되어야 하는 로직이다. 이걸 매번 외부 LLM 호출로 처리하면 트래픽이 늘어날수록 비용이 선형으로 증가해 감당이 어렵다.
- **제한(Rate Limit)**: 외부 API는 호출량 제한이 걸려 있는 경우가 많아, 트래픽이 몰리는 시점에 추천 기능 자체가 막히거나 지연될 위험이 있다. 서비스 핵심 기능이 외부 API 쿼터에 종속되는 구조는 피해야 한다.
- **근본적인 부적합**: 우리 프로젝트의 추천은 사용자 벡터와 콘텐츠 벡터 간 유사도를 0~100 점수로 정량화해서 정렬하는 방식이다. LLM은 자연어를 생성하는 모델이지 이런 수치 매칭을 일관되고 재현 가능하게 뽑아주는 도구가 아니다. 즉, 비용·제한 문제를 떠나서 애초에 우리가 필요로 하는 "점수 매기기"에는 맞지 않아 어차피 쓸 수 없다.

## 2. 자체 스코어링 방식과 향후 계획 (사용자 맞춤화)

현재는 여행 성향(`TravelStyle`)을 4개 축(계획 성향, 분위기, 역할, 활동량)으로 나누고, 사용자 벡터와 콘텐츠(장소/활동) 벡터 간 유클리드 거리를 계산해 0~100 매칭 점수로 변환하는 방식을 쓰고 있다. (`RecommendationService.matchScore`)

- 다만 지금은 사용자의 초기 벡터도, 콘텐츠에 매겨진 벡터도 모두 **우리가 임의로 부여한 값**이라는 한계가 있다.
- 계획은 여기서 멈추지 않고, **사용자의 실제 선택(클릭, 예약, 좋아요 등 행동 데이터)을 피드백으로 반영해 사용자 벡터를 점진적으로 보정**하는 것이다. 예를 들어 사용자가 특정 성향(예: 활동적인 콘텐츠)을 반복적으로 선택하면 해당 축의 점수를 그 방향으로 조금씩 이동시킨다.
- 이렇게 하면 초기에는 정적이고 임의적인 점수에서 출발하지만, 사용 데이터가 쌓일수록 점수가 실제 사용자 성향에 수렴해 개인화된 추천으로 발전한다. 외부 LLM 없이도 자체 데이터만으로 맞춤형 추천이 가능해지는 방향이다.
