# knot — 초기 화면 백엔드(인증) 기획서

> **문서 목적**: 초기 화면 흐름(랜딩 → 온보딩 → 로그인)을 지탱하는 **인증/회원 부트스트랩** 백엔드 API를 정의한다.
> **대상 독자**: 백엔드(Java / Spring) 개발자
> **짝 문서**: [01_초기화면_기획.md](01_초기화면_기획.md) (프런트엔드 화면 기획)
> **기술 스택**: Java 17+ / Spring Boot 3.x / Spring Security / Spring Data JPA / JWT
> **버전**: v1 (초기화면 한정 — 소셜 로그인 · 토큰 발급/갱신/폐기 · 회원 부트스트랩)

---

## 1. 범위 (Scope)

초기 화면에서 백엔드가 실제로 관여하는 지점은 **[5] 로그인 화면 하나**다. 랜딩·온보딩은 순수 클라이언트 화면이므로 서버 의존성이 없다.

따라서 본 문서가 정의하는 백엔드 작업은 다음으로 한정한다.

1. **소셜 로그인** — Kakao / Google OAuth 토큰 검증 후 앱 자체 JWT 발급
2. **회원 부트스트랩** — 최초 로그인 시 회원 레코드 생성, 신규/프로필완료 여부 판별
3. **토큰 갱신** — accessToken 만료 시 refreshToken으로 재발급
4. **로그아웃** — refreshToken 폐기
5. **내 정보 조회** — 로그인 직후 라우팅 판단용 `GET /users/me`

> 역할 선택·프로필 작성의 **저장 API**는 본 문서 범위 밖(후속 문서)이며, 여기서는 라우팅에 필요한 플래그(`isNewUser`, `profileCompleted`, `userType`)만 정의한다.

## 2. 공통 규약

### 2.1 응답 봉투 (Response Envelope)
모든 응답은 아래 형태를 따른다. **프런트엔드가 이미 이 구조를 파싱**하고 있으므로 반드시 유지한다.

```json
{
  "code": "SUCCESS",
  "message": null,
  "data": { /* 엔드포인트별 페이로드, 실패 시 null */ }
}
```

- `code`: 비즈니스 결과 코드 문자열. **성공은 정확히 `"SUCCESS"`** (프런트가 이 값으로 분기). 실패는 §7 에러 코드 표 참고.
- `message`: 사용자/개발자용 메시지(성공 시 `null` 허용).
- `data`: 성공 페이로드. 실패 시 `null`.

권장 구현: 공통 `ApiResponse<T>` 제네릭 래퍼 + `@RestControllerAdvice` 전역 예외 핸들러로 봉투를 일관 생성.

### 2.2 인증 방식
- **Stateless JWT (Bearer)**. 보호된 엔드포인트는 `Authorization: Bearer {accessToken}` 헤더 필요.
- accessToken/refreshToken 2종 발급. 프런트는 두 토큰을 메모리에 보관하고 모든 보호 API에 `Authorization` 헤더를 직접 부착한다(공용 인터셉터 없음).

### 2.3 Base URL / 환경
- 로컬 개발 기준 프런트는 `http://localhost:8080` (Android 에뮬레이터는 `http://10.0.2.2:8080`)을 호출한다. **서버 포트 8080 기준**으로 맞춘다.
- CORS: 개발 단계에서 위 오리진 허용. 모바일 네이티브는 Origin이 없으므로 별도 처리 불필요하나, 웹 디버그 빌드 대비 설정.

### 2.4 명명/직렬화
- JSON 필드는 **camelCase** (`accessToken`, `isNewUser`, `profileCompleted` …).
- 날짜는 ISO-8601(UTC) 문자열.

## 3. 데이터 모델

### 3.1 `users` (회원)

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | BIGINT PK | auto inc | 내부 식별자 (프런트 `userId`) |
| `provider` | VARCHAR | NOT NULL | `KAKAO` \| `GOOGLE` |
| `provider_user_id` | VARCHAR | NOT NULL | 소셜 제공자의 고유 사용자 ID |
| `email` | VARCHAR | nullable | 소셜에서 받은 이메일 |
| `nickname` | VARCHAR | nullable | 표시 이름(소셜 기본값 → 이후 수정) |
| `profile_image_url` | VARCHAR | nullable | 프로필 이미지 |
| `user_type` | VARCHAR | nullable | `KOREAN_STUDENT` \| `FOREIGN_TRAVELER` (역할 선택 전 null) |
| `profile_completed` | BOOLEAN | NOT NULL default false | 프로필 작성 완료 여부 |
| `status` | VARCHAR | NOT NULL | `ACTIVE` \| `WITHDRAWN` 등 |
| `created_at` / `updated_at` | TIMESTAMP | | 감사 컬럼 |

- **유니크 제약**: `(provider, provider_user_id)` 복합 유니크 → 동일 소셜 계정 중복 가입 방지.
- 신규 여부(`isNewUser`)는 이 레코드를 **이번 로그인에서 새로 생성했는지**로 판단.

### 3.2 `refresh_tokens` (리프레시 토큰)
| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT PK | |
| `user_id` | BIGINT FK | `users.id` |
| `token` | VARCHAR | refreshToken 값(또는 해시 저장 권장) |
| `expires_at` | TIMESTAMP | 만료 시각 |
| `revoked` | BOOLEAN | 로그아웃/회수 여부 |

> refreshToken을 DB에 저장하면 로그아웃 시 폐기·재사용 탐지가 가능하다. 단순 무상태 전략을 택한다면 이 테이블 생략 가능하나, **로그아웃 폐기 요구**가 있으므로 저장 방식을 권장.

## 4. 소셜 로그인 처리 흐름

```
[App] 소셜 SDK 로그인 → OAuth 토큰 획득
        - Kakao : accessToken
        - Google: idToken
   │  POST /auth/login { provider, accessToken }
   ▼
[Server]
   1) provider 분기
   2) 토큰 검증 → 소셜 사용자 식별자/프로필 획득
       - KAKAO : accessToken 으로 Kakao 사용자 정보 API 호출하여 검증
       - GOOGLE: idToken 서명·aud·exp 검증 (Google 공개키)
   3) (provider, providerUserId) 로 users 조회
       - 없으면 신규 생성 → isNewUser = true
       - 있으면 기존 회원   → isNewUser = false
   4) JWT accessToken / refreshToken 발급, refreshToken 저장
   5) LoginResponseData 반환
```

> **중요 — 필드명 주의**: 프런트는 Google의 경우에도 요청 바디 키를 `accessToken`으로 보내지만 **실제 값은 Google `idToken`**이다(프런트 `auth_api_service.dart` 주석 명시). 서버는 `provider == GOOGLE`이면 해당 값을 **idToken으로 간주**해 검증한다.

### 소셜 토큰 검증 상세
- **KAKAO**: 전달받은 `accessToken`으로 `GET https://kapi.kakao.com/v2/user/me` (또는 토큰 인포 API) 호출 → `id`, 이메일, 닉네임/프로필 이미지 획득. 호출 실패/401이면 토큰 무효 처리.
- **GOOGLE**: 전달받은 `idToken`을 Google 공개키로 **서명 검증** + `aud`(앱 클라이언트 ID), `iss`, `exp` 검증 → `sub`(고유 ID), 이메일, 이름 획득. (구글 `GoogleIdTokenVerifier` 사용 권장)

## 5. API 명세

### 5.1 `POST /auth/login` — 소셜 로그인 / 토큰 발급
프런트의 `AuthApiService.login(provider, oauthToken)` 이 호출.

**Request**
```http
POST /auth/login
Content-Type: application/json
```
```json
{
  "provider": "KAKAO",          // "KAKAO" | "GOOGLE"
  "accessToken": "{소셜 토큰}"   // GOOGLE 인 경우 값은 idToken
}
```

**Response 200** — `data` 페이로드는 프런트 `LoginResponseData`와 1:1 일치해야 한다.
```json
{
  "code": "SUCCESS",
  "message": null,
  "data": {
    "accessToken": "eyJhbGciOi...",   // 앱 JWT (access)
    "refreshToken": "eyJhbGciOi...",  // 앱 JWT (refresh)
    "isNewUser": true,                 // 이번 로그인에서 신규 생성 여부
    "userType": null,                  // 역할 미선택 시 null, 이후 "KOREAN_STUDENT"|"FOREIGN_TRAVELER"
    "profileCompleted": false          // 프로필 작성 완료 여부
  }
}
```

**프런트 라우팅 규칙(서버가 보장해야 하는 플래그 의미)**
| isNewUser | profileCompleted | 앱 이동 화면 |
|---|---|---|
| true | false | 역할 선택 → 프로필 설정 |
| false | false | (이탈 회원) 프로필 설정 이어서 |
| false | true | 메인 화면 |

**실패 예** (소셜 토큰 무효 등)
```json
{ "code": "INVALID_OAUTH_TOKEN", "message": "소셜 토큰 검증 실패", "data": null }
```

---

### 5.2 `POST /auth/logout` — 로그아웃 / refreshToken 폐기
**Request**
```http
POST /auth/logout
Authorization: Bearer {accessToken}
Content-Type: application/json
```
```json
{ "refreshToken": "eyJhbGciOi..." }
```

**Response 200**
```json
{ "code": "SUCCESS", "message": null, "data": null }
```
- 처리: 전달된 refreshToken을 `revoked = true` 처리(저장형) 또는 블랙리스트 등록. 프런트는 200이면 로컬 토큰을 비운다(상태코드 기반 판단).

---

### 5.3 `POST /auth/reissue` — accessToken 재발급 *(신규 정의)*
accessToken 만료 시 refreshToken으로 재발급. (프런트는 아직 미연동이나, 토큰 만료 대응을 위해 서버에서 선제 제공 권장.)

**Request**
```http
POST /auth/reissue
Content-Type: application/json
```
```json
{ "refreshToken": "eyJhbGciOi..." }
```

**Response 200**
```json
{
  "code": "SUCCESS",
  "message": null,
  "data": { "accessToken": "신규 access", "refreshToken": "신규 refresh(회전 시)" }
}
```
- refreshToken 검증(서명·만료·`revoked`·DB 존재 여부) 후 재발급. **Refresh Token Rotation** 적용 권장(재발급 시 기존 토큰 폐기, 재사용 탐지).

> ⚠️ 프런트 연동 시점은 협의 필요(§8). 우선 엔드포인트만 준비.

---

### 5.4 `GET /users/me` — 내 정보 조회 (라우팅/프로필 부트스트랩)
로그인 직후 및 앱 재진입 시 사용자 상태 동기화. 프런트 `UserProfileResponse`와 일치.

**Request**
```http
GET /users/me
Authorization: Bearer {accessToken}
```

**Response 200**
```json
{
  "code": "SUCCESS",
  "message": null,
  "data": {
    "userId": 1,
    "nickname": "현지대학생",
    "age": null,
    "userType": null,
    "profileImageUrl": null,
    "address": null,
    "addressDetail": null,
    "nationality": null,
    "languages": [],
    "visitExperience": null,
    "interests": [],
    "planningScore": null,
    "activityScore": null,
    "bio": null,
    "profileCompleted": false
  }
}
```
- 초기 화면 단계에서는 `userType`, `profileCompleted` 두 필드가 핵심(나머지는 후속 프로필 단계에서 채워짐). null 허용 필드를 그대로 내려준다.

## 6. JWT 정책

| 항목 | 권장값 |
|---|---|
| 알고리즘 | HS256(대칭, 단일 서버) 또는 RS256(키 분리 시) |
| access 만료 | 30분 ~ 1시간 |
| refresh 만료 | 14일 ~ 30일 |
| access 클레임 | `sub`(userId), `provider`, `userType`, `iat`, `exp` |
| refresh 클레임 | `sub`(userId), `jti`(폐기 추적용), `iat`, `exp` |
| 시크릿 관리 | 환경변수/Secret Manager. 소스 하드코딩 금지 |

- Spring Security 필터 체인에 **JWT 인증 필터** 추가 → `Authorization` 헤더 파싱·검증 후 `SecurityContext` 설정.
- `permitAll` 화이트리스트: `POST /auth/login`, `POST /auth/reissue`. 그 외는 인증 필요.

## 7. 에러 코드 (초기화면 관련)

| HTTP | code | 상황 |
|---|---|---|
| 200 | `SUCCESS` | 정상 |
| 400 | `INVALID_REQUEST` | 필수 파라미터 누락/형식 오류 |
| 400 | `UNSUPPORTED_PROVIDER` | provider 값이 KAKAO/GOOGLE 외 |
| 401 | `INVALID_OAUTH_TOKEN` | 소셜 토큰 검증 실패/만료 |
| 401 | `INVALID_TOKEN` | 앱 JWT 위변조/만료 |
| 401 | `EXPIRED_REFRESH_TOKEN` | refreshToken 만료/폐기됨 |
| 403 | `WITHDRAWN_USER` | 탈퇴 회원 |
| 500 | `INTERNAL_ERROR` | 서버 내부 오류 |

> 코드 문자열은 프런트가 분기에 활용할 수 있으므로 **확정 후 변경 자제**. 신규 코드는 추가만.

## 8. 협의/결정 필요 사항

- [ ] `POST /auth/reissue` 프런트 연동 시점 및 토큰 자동 갱신(인터셉터 도입) 여부.
- [ ] refreshToken **저장 방식**: DB 저장(폐기·재사용 탐지 가능) vs 무상태. → 로그아웃 폐기 요구로 DB 저장 권장.
- [ ] 신규 회원 가입 시 소셜에서 받은 닉네임/이메일 **자동 채움 범위**(개인정보 동의 범위와 연계).
- [ ] Apple 로그인 추가 시 provider 값(`APPLE`) 및 검증 방식.
- [ ] 회원 탈퇴/재가입 정책(soft delete + 재가입 시 동일 레코드 복구 여부).
- [ ] 약관/개인정보 동의 이력 저장 필요 여부(별도 `agreements` 테이블).
